moki: guide for agents

moki is a local viewer for mockups: screens, decks, short videos, diagrams and art. You write plain
HTML, CSS and JS. The user opens it in the browser, leaves notes and exports the files.
moki does not decide how a mockup looks. You decide. moki stores, serves, screenshots, exports and remembers.

URL in this guide: http://127.0.0.1:9999. If the user gave you another moki URL, use that one.


Rules

- Mockup first. Before you change UI, refactor a screen or a flow, or design a new page or feature,
  make a mockup in moki and get the user's OK. Write the real code only after that. This is not optional.
- At the start of each chat, before your first mockup, read this guide and the design skill:
    http://127.0.0.1:9999/llm-guide.txt
    http://127.0.0.1:9999/design-skill.txt
  Do not work from what you remember of an earlier chat.

2. How moki stores work

  ~/.moki/<slug>/v1/index.html     one folder per version
  ~/.moki/<slug>/v2/index.html
  ~/.moki/memory/<slug>.md         what you remember about the project
  ~/.moki/notes/<slug>.json        the user's notes and the approved version. The viewer writes it

- A slug is lowercase letters, digits and "-". For example: team-page.
- A version is one round of ideas. It can hold as many mockups as you want.
- index.html is the page the user sees first. Add any other files: pages, css, js, images, fonts.
- Do not add a light/dark toggle. The moki bar has one. Style dark mode with the dark class on <html>.
- The <title> of index.html is the project title. <meta name="description"> is the note for the version:
  say what is new in this round.


3. Tools

  list_projects(query?, all?)         the 30 newest projects, or the ones that match the query
  get_project(slug)                   versions, files, memory and open notes: call it before you work on a project
  answer_notes(slug, notes, version?) mark notes done in a version, or reply to them
  upload(slug, files | dir, ...)      make a version
  screenshot(slug, ...)               see your work
  download_project(slug, version?)    get the files back
  export(slug, format, page?, ...)    a PDF, MP4, PNG or SVG of a page
  share(slug, public)                 a link with no password. Only when the user asks
  list_memory(query?)                 the memory files, or a search of every memory
  read_memory(slug), write_memory(slug, content, append?)

upload:
- files: [{path, content}]. Add base64: true for images and fonts.
- Images: upload them with the mockup and use a relative path, for example img/logo.png.
  Never point an image at localhost, 127.0.0.1, 0.0.0.0 or another local address, for example a dev
  server. The user can open moki on another machine or with a public link, and then the image breaks.
  To use an image from a local app, save it to a file and upload it.
- dir: a folder on the moki machine. Use this when you run on the same machine: write the files to disk,
  then upload the folder in one call.
- On another machine with a shell, send the folder over HTTP. No file goes through your context:
    tar -cz -C mockup . | curl -sS --data-binary @- -H "Authorization: Bearer $TOKEN" \
      "http://127.0.0.1:9999/api/upload/<slug>?base=v3"
  The token is the one in your MCP settings. Query: base, version, delete (repeat it), check=1 for
  the sheet. Then call screenshot to see it.
- base: "v2" starts from v2. Then send only the files that changed. delete: ["old.html"] removes files.
- version: "v2" replaces v2 for a small fix. Without it, moki makes the next version.
- options: the options of the round. Section 5 has the format.
- upload refuses files that are not part of a web page (html, css, js, json, images, fonts, audio,
  video, csv, xml, wasm, 3D models, pdf), files over 10 MB, and options that do not follow the format.
  Then it saves nothing and lists each problem. Fix them and upload again. Hidden files are skipped.
- The reply has the viewer URL, warnings, and a desktop and phone sheet of index.html. Read them and fix
  what is wrong. check: false skips the sheet.

screenshot:
- versions: "v3", ["v2", "v3"] or "all". Default: the newest.
- pages: ["index.html", "b.html", "page.html?v=a"], "all", or ["options"] for each option page.
- sizes: desktop, laptop, tablet, phone, phone-landscape, slide (1280x720), square, story, or "WxH".
  Default: desktop and phone.
- themes: "light", "dark" or "both". Default: light.
- full: true takes the whole page, also when an inner element scrolls.
- selector: one element, for example "#option-b".
- One call takes up to 48 shots. They come back on one labeled sheet. sheet: false returns them one by one.

Viewer URLs: http://127.0.0.1:9999/#/p/<slug>/v3 opens index.html. Add a page to open it:
#/p/<slug>/v3/page.html?v=a. Send that link when you want the user to look at one screen.
A version with options opens the grid of the options.


4. Decks, videos, diagrams and art

A mockup can be any content that HTML can show. Three scripts in /kit do the hard parts. The comment at
the top of each script has the full list of options. Each script sets window.moki, so the viewer and
the export know what the page is.

Deck: <script src="/kit/deck.js"></script> at the end of <body>.
  <main class="deck" data-footer="Pitch · June">
    <section class="title"><h1>Title</h1><p>One line</p><small>Date</small></section>
    <section class="stats"><h2>Title</h2><ul><li><strong>87</strong>projects</li>...</ul></section>
  </main>
- Each <section> is a slide of 1280x720. data-size="1080x1080" on .deck sets another size.
- Layouts, as a class on the section: title (h1, p, small), split (two children), cards (h2, p, ul > li
  with i, b and text), stats (h2, ul > li with strong), steps (h2, ol > li with b), compare (h2, two divs
  with h3 and ul), quote (blockquote, cite), full (an svg or image fills the slide).
- Page CSS wins over the layouts. --deck-accent on .deck sets the accent color.
- Keys: arrows, G shows all slides, F full screen. ?s=3 opens slide 3.

Video: a scene in <div class="stage">, then
  <script>VIDEO = { size: '1280x720', duration: 8, fps: 30, draw(t) { /* set the scene for time t */ } }</script>
  <script src="/kit/video.js"></script>
- draw(t) must depend only on t: no CSS animation, timer or random value. Then any frame shows at any
  time, and the MP4 export gets every frame.
- video.span(t, from, to) goes from 0 to 1 between two times, eased. video.lerp(a, b, p) mixes numbers.
- ?t=2.5 shows the frame at 2.5 s with no controls. Use it with screenshot.

Diagram or art: <script src="/kit/sketch.js"></script>, then
  const s = sketch(document.querySelector('svg'), { seed: 7 })
  s.box(40, 40, 160, 72, { label: 'Agent', fill: '#fde68a' }); s.arrow(200, 76, 320, 76, { label: 'upload' })
- Shapes: line, arrow, box, circle, poly, curve, text. The same seed draws the same lines.
- Hand-drawn text uses the Caveat font: load it from Google Fonts. clean: true draws straight lines
  in the page font.

Export: the viewer has an Export button (E). The export tool makes the same files:
  any page    png (full height, 2x), pdf (one long page), files (.tar.gz of the version)
  deck        pdf (a page for each slide), zip (a PNG of each slide), png of one slide
  video       mp4, png of one frame. The MP4 needs ffmpeg on the moki machine. Up to 60 s
  drawing     svg of the biggest svg on the page
- export(slug, format, version?, page?, theme?, slide?, time?, dir?). The file comes back as a resource
  of up to 20 MB. dir writes it on the moki machine instead.
- Use it when the user asks for the file, for example "send me the deck as PDF".


5. Options

A round can show many ideas for each part. Give them as options. The viewer shows them as a grid of
cards. The user opens one option at full size, steps through the options of the part, sees its states,
and keeps the ones worth another round.

- Put each option on its own page, for example plans.html?v=a, and each state of an option on a page
  too: plans.html?v=a&s=empty.
- Give the options in the options field of upload. moki writes them to options.json in the version.
  With dir or tar, write options.json yourself:

  {
    "parts": [
      {
        "title": "Plans page",
        "size": "1280x560",
        "options": [
          { "id": "A", "name": "Three cards", "note": "Free, Pro and Team side by side.", "page": "plans.html?v=a" },
          { "id": "B", "name": "Comparison table", "note": "Plans are columns.", "page": "plans.html?v=b",
            "rec": true, "states": [{ "name": "Empty", "page": "plans.html?v=b&s=empty" }] }
        ]
      }
    ]
  }

  parts     1 or more. A part is one question of the round: a screen, the intro video, the deck cover
  title     the name of the part, up to 80 characters, unique in the version
  size      WxH of a screen card. Crop it to the part that differs. Default 1280x800. A deck or a
            video card takes the size of the page
  options   1 to 40 for each part. In the first round, give 5 or more
  id        A, B, C: up to 8 characters, unique in the part
  name      up to 80 characters
  note      one line on what is different, up to 300 characters
  rec       true for the option you recommend
  page      an .html file of the version, with a query or a #hash when it needs one
  states    other pages of the option: name (up to 40 characters) and page

- A field that is not in this list is an error. upload names each problem with its place, for example:
    options.json parts[0].options[2]: page "zz.html" is not in the version
- index.html still gives the title and the note of the version. The viewer shows the grid in its place.
- Viewer URLs: #/p/<slug>/v3 opens the grid, #/p/<slug>/v3/plans.html?v=b opens one option.
  Keys: G the grid, [ and ] the options, K keep, D desktop and phone.
- get_project lists the options of the newest version in "notes", and marks the kept ones. Build the
  next round from the kept options and drop the rest. Section 6 has the notes.


6. Notes and approval

The user can leave notes in the viewer: with the notes list open, a click on the page pins a note on
that spot. The user can also approve a version there. When the user turns on notes for a public link,
people with the link leave notes too, with their name.
- get_project returns them in "notes": the approved version, the options and the kept ones, then each
  open note with its id, version, the option, "phone" for a note on the phone, the name of a visitor,
  page, the element that was clicked and a CSS path to it, the text, and your earlier reply. Done notes
  are only counted.
- The viewer can show the page at desktop width and on a phone side by side (D). A note on the phone
  says "phone": fix the phone layout.
- Read the notes each round, and do what they say in the next version. The CSS path finds the element.
- After you upload that version, call answer_notes: {id, done: true, reply} for each note you fixed.
  The viewer shows it under "Fixed in vN" with your reply. A reply without done keeps the note open:
  use it for a question back. The user can reopen a note; then it is open again in get_project.
- When the user says "I left notes" or "see my notes", call get_project.
- While the user looks at a version, keep checking for notes and an approval in the background.
  GET /api/notes/<slug> with the agent token returns the same text as "notes" in get_project:
    until [ "$(curl -s -H "Authorization: Bearer $TOKEN" "$MOKI/api/notes/<slug>")" != "$before" ]; do sleep 30; done
  Without a background task, call get_project again before each reply.
- The approved version is the one to build. Write it to the memory too.


7. Memory

A new chat does not know the earlier rounds. The memory tells it. Each project has one markdown file,
~/.moki/memory/<slug>.md. moki only stores it. You write it and you read it.

Read:
- get_project returns the memory with the versions. read_memory(slug) returns only the memory.
- list_memory shows the first line of each file. Use it to find the project when the user does not
  give a slug.
- list_memory with query searches every memory. It returns each line that has all the words, with its
  "## vN" heading and the lines next to it. Before you start a new project, search for the same kind
  of screen or part, for example "table" or "sidebar", and follow what the user decided before.
  When a search finds nothing, try other words.
- Read the memory before each round and follow it. Do not bring back an option that the user rejected.
- When the user asks you to build the approved mockup, the memory tells you which version.
  Get its files with download_project.

Write:
- Call write_memory with append: true after each round. Start the entry with the version, "## v3".
- Make the first line of the file a one-line summary of the project.
- Write what the next chat needs: the brief, the feedback in the user's words, the decisions and why,
  the options that the user rejected, the approved version, the source of the data, open questions.
- Keep it short. Do not copy the HTML or what get_project already shows. Use the words that a later
  search will look for: the names of screens and parts.
- When the memory gets long, write_memory says so. Then make it shorter.
- Without append, write_memory replaces the file. Use it only to make a long memory shorter. Read it
  first, and keep each decision.
- Never write tokens, passwords or other secrets.

Shared memory: rules for many projects, for example the house style of one product.
- Write them to a memory of their own, for example write_memory("csema", ...): the fonts, the tokens,
  the components, what the user always asks for.
- Add a line "uses: csema" to the memory of each project that follows it. get_project then returns
  the shared memory in "shared". Names are split by commas or spaces: "uses: csema, admin".


8. Each round

1. For a project that exists, call get_project. Read the memory, the shared memory, the notes and the
   newest version.
   For a new project, search the memory with list_memory and query, and look at the user's product
   first. The design skill says how.
2. Make the mockups. Follow the design skill.
3. Upload: with base and only the changed files, with dir, or with tar over HTTP. Give the options
   of the round in options or options.json.
4. Read the sheet and the warnings. Fix and upload again with version until it looks right.
5. Call screenshot with themes: "both". Add full: true for long pages, and pages: ["options"] for
   the options.
6. Call write_memory with append: true. Write the brief, the decisions and the feedback of this round.
   If you worked on notes, call answer_notes.
7. Send the user the viewer URL and a short list of what is new. Recommend one option.

When the user gives feedback, start the next version. Do not change a version that the user approved.
